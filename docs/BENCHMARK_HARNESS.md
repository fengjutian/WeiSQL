# 基准测量装置（REQ-404）

- 命令：`npm run bench`
- 脚本：`tools/bench/run.mjs`（测量）、`tools/bench/make-bench-package.py`（合成数据包）
- 状态：装置可用；下方数字是**单机一次测量**，不是性能承诺

## 1. 它测什么

| 阶段 | 说明 |
| --- | --- |
| 数据包生成 | pyarrow 写入 Parquet + Float32 + ID Map + Manifest，固定随机种子 |
| 完整性闸门 | 用 `@weisql/cli` 的 `validatePackage(mode: "all")` 全量校验；不通过直接退出，绝不测坏数据 |
| `open()` | `NodeFileResourceReader` + `open()` 的耗时 |
| 精确检索 | 固定种子生成的查询向量，逐条计时；报告 cold / min / p50 / p95 / max / avg |
| I/O | 包装 Reader，统计 Range 请求数与读取字节数（含每次查询的均摊） |
| 内存 | 20ms 采样 `process.memoryUsage().rss` 的峰值 |
| 环境 | CPU 型号、核数、内存、平台、Node 版本一并打印 |

查询向量由线性同余生成器在脚本内生成，种子固定为 `12345`，所以两次运行可比。

## 2. ANN 对照（`--ann`）

```bash
npm run bench -- --ann --expansion-search 512
```

同一进程里先跑精确扫描、再用同一组查询跑 USearch ANN，并用精确结果作 ground truth 计算 Recall@K。

| 指标 | 精确 | ANN（`expansion_search=512`） |
| --- | --- | --- |
| p50 | 212.6 ms | 22.4 ms |
| p95 | 275.1 ms | 26.9 ms |
| Recall@10 均值 | 1.000 | **0.735** |
| Recall@10 最低 | 1.000 | **0.400** |
| 首次查询 | — | 15.2 s（含完整索引构建） |
| 进程峰值 RSS | — | 219.7 MiB（精确与 ANN 同进程） |

100,000 × 128，20 条查询，Intel Core Ultra 7 155H / 32 GiB / Node v24.14.1。

三点必须一起看：

1. **9.5 倍加速是用召回换的。** 均值 0.735 意味着平均每 10 条结果里有 2.6 条不是真近邻。
2. **均值掩盖了方差。** 逐查询召回从 0.4 到 1.0 都有；只看均值会让人误以为「大部分查询都还行」。装置因此保留 `perQuery`。
3. **小规模下 ANN 反而更慢。** 5,000 × 32 时 ANN p50 11.8 ms，精确约 10 ms——构建与图遍历开销在数据量小时占主导，ANN 不是无条件加速。

### 2.1 召回取决于数据分布（实测）

`--clusters N --cluster-spread S` 生成 N 个高斯簇（`S` 越小越紧），其余参数不变：

| 分布（100k × 128） | `expansion_search` | Recall@10 均值 | 最低 | 索引构建 |
| --- | --- | --- | --- | --- |
| 均匀随机 | 512 | 0.735 | 0.400 | 15.2 s |
| 100 簇，spread 1.0（重叠） | 512 | 0.740 | 0.100 | 3.0 s |
| 100 簇，spread 0.35 | 512 | 0.685 | 0.000 | 2.7 s |
| 10 簇，spread 0.35 | 512 | 0.590 | 0.000 | 6.1 s |
| 100 簇，spread 0.1（很紧） | 512 | **0.385** | 0.000 | 5.2 s |
| 100 簇，spread 0.1 | 2048 | 0.760 | 0.000 | 3.3 s |

**这推翻了本文早先的一个假设：均匀随机并不是 HNSW 最不利的情形。** 簇越紧，真实 Top-10 越是「几乎等距的近重复点」，微小的近似误差就会改变集合重叠，Recall 大幅下降；把 `expansion_search` 提高 4 倍只能把 0.385 恢复到 0.76，最低值仍是 0——有些查询永远回不来。

因此：**任何 ANN 召回数字都必须连同数据分布一起报告**，并且必须在目标数据上测量。聚类混合只是比均匀噪声更接近真实 embedding 的形状，仍然不是真实数据。装置输出的 `distribution` 字段会记录实际使用的分布。

## 3. 全文检索（`--text`）

```bash
npm run bench -- --text
```

同一合成包增加 `body` 列（5000 词表、Zipf 分布、每文档 30–70 词），用真实生成器
`tools/build-text-index.mjs` 建索引，再测 BM25 查询延迟。

| 指标 | 100,000 文档 |
| --- | --- |
| 词项数 / 平均文档长度 | 5,000 / 50 tokens |
| 索引总大小 | 74.2 MB（742 B/文档） |
| ├ 倒排表 `terms.jsonl` | 36.7 MB |
| ├ 文档正文 `documents.jsonl` | 33.1 MB |
| ├ ID Map | 4.0 MB |
| ├ 文档长度 `doclengths.bin` | 0.4 MB |
| └ 词项偏移 | 40 KB |
| 构建耗时 | 4.5 s（含读取 Parquet 文本列） |
| 查询 p50 | **10.2–10.8 ms**（三次重复） |
| 查询 p95 | 15–24 ms |
| 首次查询 | 160–223 ms |

三点解读：

1. **正文占索引 45%。** 只有需要 RAG 组装上下文时才应生成 `documents`；不生成时索引约 41 MB。这个取舍由生成器的可选项决定。
2. **延迟由固定开销 + 每命中一次随机读构成。** `doclengths.bin`（400 KB）每次查询都要整读，这是固定成本；每个返回命中还要做一次 ID Map 随机读。同一数据集下 `--topk` 的影响（p50）：topK=1 → 8.1 ms，5 → 9.1 ms，10 → 16.1 ms，20 → 15.0 ms（单次运行、有噪声）。因此「10 ms 级」不是语料大小决定的：5,000 文档时 p50 仍有约 12 ms。
3. **首次查询慢一个数量级。** 它包含词项偏移与倒排表的首次读取；后续查询命中 OS 页缓存。

与 ANN 不同，**BM25 没有召回率可报告**：它是精确排序，不存在「牺牲召回换速度」。因此这里只报告延迟与体积。

## 3.1 RRF 的 k 敏感性（`--fusion`）

```bash
npm run bench -- --fusion
```

对同一批查询分别用 `k = 10/30/60/100/200` 跑 `db.hybrid.search`，把结果与 `k = 60` 的基线比较。

| k | Top-10 平均重合 | 最低 | Top-1 变化（/20） | 平均名次位移 |
| --- | --- | --- | --- | --- |
| 10 | 0.99 | 0.90 | 2 | 0.09 |
| 30 | 1.00 | 1.00 | 1 | 0.04 |
| 60（基线） | 1.00 | 1.00 | 0 | 0.00 |
| 100 | 1.00 | 1.00 | 0 | 0.00 |
| 200 | 1.00 | 1.00 | 0 | 0.00 |

100,000 文档 × 128 维，20 组（向量查询, 文本查询）对，每路取 40 个候选。

两点解读：

1. **k ≥ 30 时排序完全一致。** 当 `k` 远大于候选列表长度（这里 40）时，`1/(k + rank)` 的差异被压平，排序主要由「出现在哪几路」决定，而不是名次细节。k=60 落在这个平坦区间内。
2. **只有 k=10 会改变结果**，且只影响 2/20 个查询的 Top-1。这说明默认 60 是安全值，但**不说明 60 排序更正确**——本实验没有相关性标注，衡量的是稳定性而非质量。要回答「哪个 k 更好」，需要带标注的数据集。

## 3.2 过滤查询的 I/O 与延迟（`--filter`）

```bash
npm run bench -- --filter
```

真实 DuckDB 过滤（`exact-filter-first`），测量向量读取量与端到端延迟。

| 查询 | 向量字节/查询 | ID Map 字节/查询 | 向量请求/查询 | p50 |
| --- | --- | --- | --- | --- |
| 无过滤 | 51.2 MB | 仅 Top-K | 98 | 156.2 ms |
| `id >= doc-099000`（尾部 1000 行） | **0.51 MB** | **480 B** | **1** | **17.1 ms** |
| `category = alpha`（约 1/3，散乱） | 51.2 MB | **475 B** | 98 | 175.3 ms |

100,000 × 128，10 次采样，单机热缓存；p50 是 10 次查询的中位数，首次查询包含索引加载。

三点解读：

1. **反向索引是决定性的**：`ID → row` 改为一次加载、内存二分后，窄过滤从 327 ms 降到 17 ms，ID Map 读取从每查询 4.0 MB 降到 480 B。
2. **宽过滤也受益**：向量仍要读 51.2 MB，但省掉 ID Map 扫描后从 526 ms 降到 175 ms，已接近无过滤基线。
3. **实现方式比结构更重要**：最初逐条二分读取索引，1000 次查询发出约 17,000 次 range 请求，延迟反而升到 5.4 s。整份索引一次载入（3.2 MB，小于被替代的 ID Map）再在内存二分，才得到上面的数字。

## 3.3 DuckDB-Wasm 物化与过滤（`bench:wasm`）

```bash
npm run bench:wasm                          # 50k / 200k / 500k 行
npm run bench:wasm -- 50000 200000 500000
```

它用 `@duckdb/duckdb-wasm/blocking` 在 Node 里跑**与浏览器相同的 WASM 构建与适配器代码**，
先生成低压缩率的 Parquet（32 字符随机 id、随机 score），再测量 `open()`（扩展 + 物化 + L4）
与一次等值过滤查询的时间，以及显式 GC 后的 RSS/`external` 增量。

| 行数 | Parquet | `open()` | 过滤查询 | RSS 增量 | external 增量 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 50,000 | 1.9 MB | 160 ms | 5.9 ms | ~24 MB | ~9 MB |
| 200,000 | 7.5 MB | 192 ms | 7.9 ms | ~43 MB | ~30 MB |
| 500,000 | 18.8 MB | 298 ms | 12.9 ms | ~76 MB | ~73 MB |

读法：物化耗时约 0.6 ms / 1000 行；RSS 增量约为 Parquet 的 4 倍（Parquet 字节 +
WASM 堆里的 VFS 副本 + 物化表）。`maxTableBytes`（默认 256 MiB）是拒绝阈值，不是内存保证。

**边界**：这是 Node 里的 WASM 测量，不是浏览器测量；没有 DOM/Worker 开销，
也没有跨网络加载 34 MB WASM 的冷启动。浏览器侧只有 `probe:wasm` 的 3 行数据。

### 散乱过滤暴露的阈值问题

`--filter` 现在还测量一个散乱的选择性：`score >= 87500`（约 1/8 的行，随机分布）。

| 查询 | 向量字节/查询 | 向量请求/查询 | p50 |
| --- | --- | --- | --- |
| `id >= doc-099000`（连续尾部 1000 行） | 0.51 MB | 1 | 15.1 ms |
| `score >= 87500`（散乱 ~1/8） | 51.2 MB | 490 | 135 ms |
| `score >= 75000`（散乱 ~1/4） | 51.2 MB | 490 | 184 ms |

最初只按「允许行是否 ≤ 集合的 1/8」决策，散乱 1/8 会命中这条规则：读取 6.4 MB，但拆成 **54,395 次**单行请求，p50 **4.2 s**——比顺序扫描慢 30 倍，尽管字节少了 8 倍。

修正为**请求感知的成本模型**：估算 `允许字节 + 每次请求开销` 与 `整文件字节 + 块数开销` 取较小者。每请求开销按实测约 11 KB 计，取 12 KB（保守）：

- 连续尾部（1 次请求）继续走选择性读取；
- 散乱 1/8 回退到顺序扫描，p50 从 4.2 s 降到 **135 ms**；
- 测试同时锁住三个方向：窄连续（选择性）、散乱一半（顺序）、散乱 1/8（顺序）。

## 3.3 量化对 Recall 与索引体积的影响（`bench:quantization`）

```bash
npm run bench:quantization -- --rows 50000 --dimension 128 --queries 20 --expansion 256
```

同一批合成向量分别建 f32 / f16 / i8 索引，用精确检索做 ground truth。

| 量化 | Recall@10 | p50 | 构建 | 索引体积 | 相对 f32 |
| --- | --- | --- | --- | --- | --- |
| f32 | 0.81 | 2.94 ms | 3.2 s | 31.50 MB | — |
| f16 | 0.775 | 1.88 ms | 3.9 s | 19.29 MB | −39% |
| i8 | 0.785 | 2.00 ms | 2.5 s | 13.19 MB | −58% |

50,000 × 128，均匀随机向量，`connectivity=16`、`expansion_search=256`，20 条查询。`expansion_search=128` 时三者召回降到约 0.66（构建 2.9–5.7 s），说明召回主要由搜索参数决定。

解读：

1. **体积换召回是单调的**：f16 省 39% 体积、召回低 3.5 个点；i8 省 58%、低 2.5 个点（i8 与 f16 的差距在 200 次命中的噪声内）。
2. **基线不高**（f32 0.81），因为均匀随机 128 维是 HNSW 最不友好的分布；真实 embedding 通常成簇，同参数下召回会更高。**这些数字不能外推到真实语料。**
3. **一次被定位的测量 bug**：最初 50k 构建耗时 236 s，并伴随不稳定的召回。原因是调用 `index.add(keys, vectors, rows)`——USearch 的第三个参数是**线程数**，不是数量，等于请求了 5 万个线程。修正后构建 2.5–5.7 s、召回稳定。上一版本记录里把它当成「未解释的异常」；正确结论是**基准脚本错了，库没问题**。
4. 查询延迟差异在毫秒级噪声内，量化主要是体积与召回的交易，不是延迟优化。

### 成簇数据上的对照

真实 embedding 通常成簇，均匀随机是最不利的分布。同一批 50k × 128、64 个簇、`expansion_search=256`：

| 量化 | Recall@10 | p50 | 构建 | 索引体积 |
| --- | --- | --- | --- | --- |
| f32 | 1.00 | 0.88 ms | 1.8 s | 31.50 MB |
| f16 | 1.00 | 0.40 ms | 1.6 s | 19.29 MB |
| i8 | 0.905 | 0.33 ms | 0.8 s | 13.19 MB |

- **f16 在成簇数据上无损**：召回与 f32 相同，体积小 39%；
- **i8 掉 9.5 个点，且提高 `expansion_search` 到 512 也没有恢复**（仍为 0.905）。说明损失来自量化本身，不是搜索窗口；
- 因此若将来引入量化，应优先 **f16**；i8 若要可用，需要保留 f32 做重排（rescoring），而那会抵消大部分体积收益。

因此：**暂不把量化写进格式**。f16 是候选项，i8 需要重排方案；两者都以真实语料验证为前提。

两个基准都带 `--self-test`，并由 `npm run bench:self-test` 在 CI 中执行：量化自检断言 `f32 > f16 > i8` 的体积顺序与搜索结果数量，召回自检用内存生成的 `.npy` 走完整解析与计算路径。它们守的是基准脚本本身——上一轮正是脚本把线程数当成向量数量，才产生了假异常。

## 3.4 浏览器流式读取（`bench:wasm-stream`）

```bash
npm run bench:wasm-stream
```

在真实 Chromium 中分两段测量，启动参数带 `--enable-precise-memory-info`，堆增量取自
`performance.memory`：

1. **纯交付路径**：`db.sqlStream("select range as n from range(N)")`，看首行、总耗时、行/秒；
2. **真实 Parquet**：Node 端生成 20 万 / 50 万行的 Parquet 包，经 HTTP Range + L3 校验后
   `open()` 物化，再用 `sqlStream()` 读取，并与 `db.sql()` 的数组结果对照。

合成行（只测交付路径）：

| 模式 | 行数 | 首行 | 总耗时 | 行/秒 | 堆增量 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `sqlStream` | 100,000 | 16 ms | 126 ms | 794k | ~1.3 MB |
| `sqlStream` | 1,000,000 | 5 ms | 871 ms | 1.15M | ~11.3 MB |
| `sqlStream` | 5,000,000 | 6 ms | 4,542 ms | 1.10M | ~14 MB |
| `db.sql` | 100,000 | — | 66 ms | — | 噪声大，不作结论 |

真实 Parquet：

| 行数 | Parquet | `open()` | open 堆 | `sqlStream` | 首行 | 流式堆 | `db.sql` | 数组堆 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 200,000 | 7.5 MB | 1,963 ms | +10.6 MB | 430 ms（465k 行/s） | 17 ms | +19.9 MB | 362 ms | +40.6 MB |
| 500,000 | 18.8 MB | 2,430 ms | +21.9 MB | 2,165 ms（231k 行/s） | 23 ms | 回收后 ~0 | 2,035 ms | +95.4 MB |

读法：

- 首行在 5–23 ms 到达，说明交付是增量的，不是等整表算完；
- 合成 500 万行只带来 ~14 MB 堆增量，行在消费后即可回收；
- 真实 Parquet 场景里 `db.sql()` 的数组堆增量随规模近似线性上升（40.6 → 95.4 MB），
  流式则没有同等增长（20 万行 +19.9 MB，50 万行在 GC 后回到 ~0）；
- 50 万行的流式吞吐（231k 行/s）明显低于 20 万行（465k 行/s），说明规模变大后
  Arrow batch 转换与 GC 开始成为瓶颈，不能按线性外推；
- 这些是单次运行的数字，随 GC 与机器状态波动（同一台机器上一次 500 万行是 6.8 s），只用于判断量级，不是吞吐承诺。

## 3.5 浏览器冷启动（`bench:wasm-cold`）

```bash
npm run bench:wasm-cold
```

用 CDP `Network.setCacheDisabled(true)` 关掉 HTTP 缓存，并给 WASM/worker URL 加 `?cold=1`，
测量从导航到 `open()` 完成（下载 + 实例化 + parquet 扩展 + 物化 3 行表）的时间：

| 指标 | 结果 |
| --- | --- |
| `open()`（冷缓存） | 1,817 ms |
| `duckdb-eh.wasm` | 32.7 MB |
| `parquet.duckdb_extension.wasm` | 2.9 MB |
| `duckdb-browser-eh.worker.js` | 0.7 MB |

这是本地静态服务器上的数字：没有 CDN、没有网络 RTT、也没有并发竞争，因此只说明

CDN + 冷缓存 + 移动网络验收。

## 4. 记录结果（2026-10-30，单机）

环境：Intel Core Ultra 7 155H · 22 核 · 32 GiB · Windows 10.0.26200 x64 · Node v24.14.1

| 规模 | 向量字节 | 校验 | open | p50 | p95 | max | 峰值 RSS | 每查询读取 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 5,000 × 32 | 640 KB | 36 ms | 0.4 ms | 9.8 ms | 13.8 ms | 13.8 ms | 56 MiB | 640 KB |
| 100,000 × 128 | 51.2 MB | 437 ms | 0.5 ms | 151.3 ms | 176.9 ms | 184.7 ms | 112 MiB | 51.2 MB |

可读出的事实：

- **精确检索每次查询都要完整扫一遍向量文件**：`rangeBytesPerQuery` 恰好等于 `vectorBytes`。分块读取降低的是峰值内存，不是总 I/O，这一点与文档一致。
- 100k × 128 的 20 次查询共 2,360 个 Range 请求，即每查询约 118 个块（10 万行 ÷ 1024 行/块）。
- 峰值内存 112 MiB，远小于向量文件 51.2 MB 的两倍——分块解码生效，而不是把文件整体载入。
- `open()` 不做预读，所以是亚毫秒级；真正的成本在第一次查询。

### 测量噪声（2026-10-31 补充）

同一台机器、同一命令复跑时，如果后台还有别的进程（当时是一个占用约 45% CPU、1.6 GB 的 node 进程），数字会显著漂移：

| 指标 | 空闲时（§4 记录值） | 带负载复跑 |
| --- | --- | --- |
| 精确检索 p50（100k × 128） | 151.3 ms | 271 ms |
| 文本检索 p50 | 10.2–10.8 ms | 27.3 ms |

因此：**这些数字只在空闲单机内可比**。跨机器、跨负载的比较没有意义，文档保留空闲时的记录值，不因一次带负载的复跑而修改。基准输出已包含 `environment` 字段（平台、CPU 型号、核数），便于判断两次结果是否在同一条件下取得。

## 5. 明确不作数的部分

- **不是性能承诺**：单机、单次运行、热页缓存（校验已经读过全部文件）。没有多机复现，也没有冷缓存对照。
- **不含浏览器**：浏览器端没有端到端耗时数据；`bench:wasm` 是 Node 里的 WASM 测量。
- **不含 ANN**：只有精确扫描基线，不能据此推断近似索引的延迟或召回。
- **不含百万级**：100 万 × 768 约 3 GB，本机未跑；`BENCHMARK_PROTOCOL_V1.md` 要求同时报告内存与下载量，单机也不足以代表 CDN 场景。
- **不含 SQL 引擎对比**：`bench:wasm` 只测 DuckDB-Wasm 自己的物化与查询，不与 Node DuckDB 比较吞吐。

## 6. 复现

```bash
npm run bench                                   # 100k x 128, 20 条查询
npm run bench -- --rows 20000 --dimension 64 --queries 10
npm run bench -- --package ./bench/pkg-5000x32  # 复用已生成的包
npm run bench:wasm                              # DuckDB-Wasm 物化与过滤
npm run bench:wasm -- --smoke                   # 1k 行，CI 里跑冒烟
npm run bench:wasm-stream                       # Chromium 中的流式读取
```

生成的包写入 `bench/`（已加入 `.gitignore`）。合成包依赖 Python + pyarrow；测量本身只需要 Node。

如果需要把这些数字写进对外材料，前提是：换一台机器复现、注明冷/热缓存、并补充浏览器侧数据。否则只能当作开发期基线。
