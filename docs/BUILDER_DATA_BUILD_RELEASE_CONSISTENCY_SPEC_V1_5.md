# WeiSQL AI Builder 数据构建与发布一致性规范 V1.5

文档编号：WSAI-BUILDER-SPEC-001 · 版本：V1.5 · 状态：设计规范草案 · 适用阶段：V1 首版

本规范承接 WeiSQL AI 的《需求规格说明书 V0.9》《API Contract V1.0》《Runtime 执行语义与一致性规范 V1.1》《工程实施规范 V1.2》《资源读取层设计规范 V1.3》和《向量搜索核心算法与一致性规范 V1.4》。

本文聚焦一个关键问题：如何把源数据、Parquet 数据文件、向量数据、行 ID 映射、向量索引和 Manifest 可靠地构建成一个可验证、可发布、可供 Runtime 读取的数据包。

本文定义目标行为、数据格式、构建状态机、校验规则和验收标准。示例代码和配置属于设计参考，尚不代表已在真实环境中编译或通过测试。

### 与当前仓库的差异

Builder 的**核心链路已实现**（`buildPackage()`，`packages/sdk/src/builder.ts`），但与本文的目标存在出入：

| 本文的设计 | 当前仓库的实际状态 |
| --- | --- |
| 输入 JSONL → 生成 Parquet → 构建索引 的完整链路 | **未实现**。V1 Builder 只消费**已存在的 Parquet**，不负责 CSV/JSON 推断与生成 |
| 构建向量索引 | 未实现。Manifest 的 `index` 字段缺 connectivity / expansion 等构建参数，无法复现同一索引 |
| 构建状态机 | 已实现：`CREATED → VALIDATING → BUILDING → VERIFYING → PUBLISHING → PUBLISHED`，失败进入 `FAILED` 并清理暂存区 |
| 发布前自检 | 已实现：暂存区重新读取做 L1/L2/L3 自检；未提供 `rowIds` 时如实报告 `id-membership-unverified` 警告而非假装通过 |
| 原子发布与覆盖保护 | 已实现：默认拒绝覆盖已有目录；`overwrite: true` 时先移走旧目录，成功才删除，失败则回滚 |
| 生成真实摘要与字节数 | 已实现：真实 SHA-256 与字节数，非占位值 |

## 1. 设计目标与范围

### 1.1 核心目标

构建一致性

确保 Parquet 行、向量行、ID 映射和索引记录使用同一套稳定的行标识，不发生错位。

发布前完整校验

在发布之前验证 Manifest、文件长度、SHA-256、向量维度、索引兼容性及引用关系。

原子化发布

构建失败时不暴露半成品；发布新版本时不破坏现有可用版本。

可恢复、可追溯

保留构建日志、输入摘要、配置和失败阶段，支持安全重试及问题定位。

### 1.2 V1 范围

| 功能           | V1 要求 | 说明                           |
| ------------ | ----- | ---------------------------- |
| 数据导入         | 必须    | JSONL、CSV；其他格式通过导入适配器扩展      |
| Parquet 生成   | 必须    | 统一字段类型、Schema 和分片规则          |
| 向量数据导入       | 必须    | 接受外部生成的 Embedding，支持独立向量文件   |
| 行 ID 映射      | 必须    | 保证 SQL 记录和向量记录对应             |
| 向量索引构建       | 必须    | 通过 Vector Index Adapter 隔离引擎 |
| Manifest 生成  | 必须    | 描述文件、Schema、向量集合及索引          |
| 完整性校验        | 必须    | 发布前强制执行                      |
| 临时目录与发布      | 必须    | 构建与正式发布分离                    |
| 失败恢复         | 必须    | 可识别失败阶段，安全清理或重试              |
| 增量构建         | 预留    | 首版不承诺通用增量索引维护                |
| 数据写入 Runtime | 不支持   | V1 Runtime 以只读为主             |
| 多数据集事务       | 不支持   | 不提供跨多个发布目标的事务保证              |

## 2. Builder 总体架构

### 2.1 模块划分

输入层：Source Adapters

JSONL / CSV / Parquet / 外部 Embedding

规范化层：Normalization

Schema、字段类型、主键、空值、重复记录和数据质量规则

SQL 数据构建

Parquet 分片、行数、Schema、分区元数据

向量数据构建

向量校验、行映射、ID 文件、索引构建

一致性验证与 Manifest 生成

跨文件关联、哈希、数量、维度、索引兼容性

Staging → Verify → Publish

临时构建、完整验证、发布不可变版本

### 2.2 核心模块职责

| 模块                  | 职责                   | 不负责                        |
| ------------------- | -------------------- | -------------------------- |
| `source-adapters`   | 读取输入数据、统一读取接口        | 决定向量索引算法                   |
| `normalizer`        | 类型转换、Schema 校验、主键处理  | 修改已经发布的数据包                 |
| `parquet-writer`    | 生成 Parquet 文件及统计信息   | 生成 ANN 索引                  |
| `vector-ingest`     | 验证向量、行序和维度           | 生成业务文本 Embedding，除非另接模型适配器 |
| `id-map-builder`    | 生成 SQL 行与向量行的映射      | 解释业务字段                     |
| `index-adapters`    | 调用 USearch 等索引后端     | 改变公共 Manifest 语义           |
| `manifest-writer`   | 生成包描述文件              | 单独宣告数据已通过校验                |
| `package-validator` | 验证文件、映射、索引与 Manifest | 自动修复未知的数据错位                |
| `publisher`         | 发布不可变版本并更新可选指针       | 覆盖现有版本文件                   |
| `build-journal`     | 记录阶段、摘要、耗时和错误        | 替代最终完整性校验                  |

## 3. 标准数据包布局

V1 使用多文件数据包。先保证可验证、可增量读取，再决定是否需要单文件 `.wsql` 封装。

```
my-dataset/
├── manifest.json
├── data/
│   ├── part-00000.parquet
│   └── part-00001.parquet
├── vectors/
│   └── document-embedding/
│       ├── vectors.f32
│       ├── id-map.jsonl
│       └── id-map.offsets
├── indexes/
│   └── document-embedding/
│       ├── usearch.index
│       └── index-meta.json
└── metadata/
    ├── schema.json
    └── build-info.json
```

`manifest.json` 是数据包的入口描述；`build-info.json` 是诊断与追溯材料。两者不能混淆：构建日志或内部路径不应成为 Runtime 必须依赖的运行条件。

### 3.1 文件职责

| 文件                | 内容                   | 是否必须               |
| ----------------- | -------------------- | ------------------ |
| `manifest.json`   | 数据包格式、文件清单、集合定义、校验摘要 | 必须                 |
| `data/*.parquet`  | SQL 可查询的数据           | 必须                 |
| `vectors.f32`     | 行优先 Float32 向量       | 有向量集合时必须           |
| `id-map.jsonl`    | 向量行与业务 ID、数据行之间的映射   | 有向量集合时必须           |
| `id-map.offsets`  | JSONL 记录偏移量          | 采用随机行读取时必须         |
| `usearch.index`   | ANN 索引文件             | 使用 USearch ANN 时必须 |
| `index-meta.json` | 索引后端、维度、度量、参数和构建信息   | 有 ANN 索引时必须        |
| `schema.json`     | 可选的 Schema 独立副本      | 推荐                 |
| `build-info.json` | 输入摘要、构建器版本、诊断信息      | 推荐                 |

一致性要求： Manifest 中引用的文件必须存在；所有必须的文件必须被清单覆盖。不能只校验 Manifest 引用的文件，而忽略目录内意外出现的未登记文件。V1 可以将未登记文件视为警告或错误，由发布配置明确选择；正式发行默认严格模式报错。

## 4. 稳定行标识与跨文件一致性

这是整个 Builder 最重要的设计约束之一。

### 4.1 不允许依赖偶然的行顺序

不能假定以下两个独立操作会得到相同顺序：

- SQL 导入后生成 Parquet；
- 外部 Embedding 服务返回向量；
- 向量索引后端内部重排记录；
- 分片合并或重新构建。

即使两次操作都基于同一个 CSV，排序、空值过滤和并行处理也可能改变行顺序。

因此，Builder 必须使用稳定业务 ID 或构建期稳定记录 ID建立显式映射。

### 4.2 推荐映射模型

以 `documents` 表为例：

| `row_id` | `document_id` | `content` | 向量状态 |
| -------- | ------------- | --------- | ---- |
| 0        | `doc-a`       | 文档 A      | 已生成  |
| 1        | `doc-b`       | 文档 B      | 已生成  |
| 2        | `doc-c`       | 文档 C      | 已生成  |

`row_id` 是当前数据包中的稳定整数行号；`document_id` 是业务主键。两者用途不同：

- `row_id`：高效读取向量和建立索引。
- `document_id`：跨数据版本关联业务实体。
- `data_row_ref`：指向 Parquet 分片和行位置，或映射到单独的稳定行目录。

首版建议： 统一采用 Builder 生成的 `row_id`，所有导入、向量生成、索引构建都使用同一份规范化记录清单作为事实来源。若输入数据有重复主键，必须由配置明确规定拒绝、覆盖还是聚合；默认拒绝。

### 4.3 数据包内部一致性约束

设 SQL 规范化后共有 \\(N\\) 条记录，向量集合的有效记录数为 \\(M\\)。

对于要求每条记录都有向量的集合：

\\[ N=M \\]

对于允许缺失向量的集合：

\\[ 0 \leq M \leq N \\]

但必须显式记录缺失策略和映射关系，不能通过删除空向量后默认假定剩余向量仍与 SQL 行号一一对应。

若只对部分记录建立向量索引，索引中的每个标签必须能映射回有效 `row_id`，且不能出现重复标签或越界标签。

## 5. 标准构建流水线

### 5.1 阶段定义

### 01

CREATED

接收构建配置，建立任务 ID 和 staging 目录

### 02

VALIDATING

校验源文件、Schema、字段映射和向量输入配置

### 03

NORMALIZING

规范化字段、主键、空值与记录顺序

### 04

BUILDING_DATA

写入 Parquet 分片及行目录

### 05

BUILDING_VECTORS

校验向量、生成 Float32 文件和 ID 映射

### 06

BUILDING_INDEX

构建 ANN 索引并写入 index-meta.json

### 07

WRITING_MANIFEST

登记文件、Schema、计数、哈希与兼容信息

### 08

VERIFYING

重新读取并验证所有产物及跨文件一致性

### 09

PUBLISHING

发布不可变版本，必要时更新版本指针

### 10

PUBLISHED

输出最终路径、摘要、构建报告

`FAILED` 是任一阶段发生不可恢复错误后的终态；`CANCELLED` 用于用户主动取消。恢复时不应简单地从上次日志中读取阶段编号并盲目续跑，而应验证已完成阶段的产物是否仍然存在、配置是否一致、摘要是否匹配。

### 5.2 每个阶段的提交条件

| 阶段         | 通过条件                    | 失败处理        |
| ---------- | ----------------------- | ----------- |
| 输入校验       | 输入可读，Schema 与配置合法       | 不创建正式版本     |
| 规范化        | 主键策略、类型转换、空值规则全部通过      | 保存错误报告，停止   |
| Parquet 构建 | 文件可读、行数和 Schema 与记录清单一致 | 丢弃不完整分片     |
| 向量构建       | 向量维度、数值范围、映射和行数满足策略     | 禁止进入索引构建    |
| 索引构建       | 后端返回成功，索引元数据与向量集合一致     | 删除或隔离无效索引   |
| Manifest   | 所有文件引用可解析、格式版本合法        | 不发布         |
| 完整验证       | 全量必需检查通过                | 不发布         |
| 发布         | 新版本目录完整且可读取             | 保留旧版本，不切换指针 |

## 6. 源数据规范化

### 6.1 输入格式

V1 最低支持：

- CSV：明确分隔符、编码、表头和空值规则。
- JSONL：每行一个 JSON 对象。
- Parquet：直接读取并校验 Schema。
- 外部向量文件：必须提供行 ID 或可验证的业务主键映射。

不同输入适配器最终输出统一的内部记录结构，不应让 SQL Writer 或 Vector Builder 直接处理各自不一致的原始格式。

### 6.2 Schema 规则

构建配置应定义：

- 表名与字段名；
- 字段类型及允许的类型转换；
- 主键字段；
- 可空字段；
- 时间、日期、Decimal、二进制数据的转换策略；
- 是否允许额外字段；
- 重复主键处理策略；
- 无效行处理策略。

默认原则是失败优先于静默修复。例如，字符串 `"abc"` 无法转换为整型时，不能悄悄写成 `0`。

### 6.3 数据质量报告

至少输出以下统计：

| 指标       | 用途            |
| -------- | ------------- |
| 输入记录数    | 与规范化结果比较      |
| 接受记录数    | 进入数据包的记录数     |
| 拒绝记录数    | 无效记录数量        |
| 主键重复数    | 检测数据身份冲突      |
| 类型转换失败数  | 检测 Schema 不兼容 |
| 空值统计     | 判断向量生成与查询条件风险 |
| 分片数、分片大小 | 检查构建和读取成本     |

若配置为 `invalidRows: "reject"`，任何无效行都导致构建失败；若未来支持 `skip`，必须把拒绝数量和原因写入构建报告，且 Manifest 中的有效行数必须反映实际发布数据，而非输入行数。

## 7. Parquet 数据构建规范

### 7.1 分片策略

Parquet 按分片写入，而不是一次性把所有数据聚合在内存中。

分片策略至少支持按最大行数或近似文件大小切分。初始建议：

- 目标文件大小：64–256 MiB，作为待基准测试的默认区间；
- 记录顺序：按规范化输入顺序或明确指定的稳定排序；
- 分片编号：从 `part-00000.parquet` 开始连续编号；
- 每个分片记录行数、Schema 摘要、文件长度和 SHA-256。

上述文件大小是工程初始建议，不是已经验证的最优参数。

### 7.2 写入后验证

每个 Parquet 文件必须重新打开并验证：

1. 文件可被目标 SQL 引擎读取；
2. 实际 Schema 与预期 Schema 兼容；
3. 实际行数与写入统计一致；
4. 字段类型未发生意外转换；
5. 分片之间 Schema 一致；
6. 分片的记录范围无重叠或遗漏。

如果 Runtime 需要通过 `row_id` 定位到某一条记录，应额外生成行目录或明确规定 `row_id` 到分片、分片内行号的计算方式。不能只凭文件名推断行号。

### 7.3 SQL 行定位模型

推荐为每个分片登记：

```
{
  "path": "data/part-00000.parquet",
  "rowCount": 100000,
  "rowIdStart": 0,
  "rowIdEndExclusive": 100000
}
```

第二个分片从上一个分片的 `rowIdEndExclusive` 开始。区间采用左闭右开形式：

\\[ [\text{rowIdStart},\text{rowIdEndExclusive}) \\]

必须满足：

- 第一个分片从 `0` 开始；
- 每个分片 `rowCount = rowIdEndExclusive - rowIdStart`；
- 相邻分片区间连续；
- 全部区间无重叠；
- 最后一个分片的结束位置等于总行数。

如果未来支持按主键排序、分区重排或增量合并，则必须重新生成相关映射，不能复用旧版本的行号映射。

## 8. 向量导入与索引构建

### 8.1 向量输入契约

每个向量集合至少需要以下配置：

| 属性                    | 要求                    |
| --------------------- | --------------------- |
| `collectionName`      | 唯一集合名称                |
| `source`              | 向量来源及输入格式             |
| `dimension`           | 固定正整数                 |
| `dtype`               | V1 固定为 `float32`      |
| `metric`              | `cosine`、`l2` 或 `ip`  |
| `rowMapping`          | 业务 ID 或 `row_id` 映射方式 |
| `missingVectorPolicy` | `reject` 或显式配置的缺失处理策略 |
| `indexBackend`        | 索引适配器名称及版本            |
| `indexParameters`     | 经验证的后端参数              |

V1 不应假设 Builder 必须负责调用 Embedding 模型。向量生成属于可插拔的上游阶段；Builder 的核心职责是校验、对齐、持久化和索引构建。

### 8.2 向量文件格式

`vectors.f32` 采用：

- Float32；
- 小端序；
- 行优先（row-major）；
- 无文件头，维度和行数由 Manifest 声明。

第 \\(i\\) 行、第 \\(j\\) 维元素的字节偏移为：

\\[ \operatorname{offset}(i,j)=(iD+j)\times4 \\]

其中 \\(D\\) 为维度。

文件大小必须满足：

\\[ \operatorname{bytes}=N_v\times D\times4 \\]

其中 \\(N_v\\) 是实际写入向量数。

Builder 必须验证：

- 所有向量维度一致；
- 所有元素均为有限值；
- 量化、归一化等预处理与集合配置一致；
- cosine 集合拒绝零向量；
- 不能静默截断、补零或改变向量维度；
- 目标索引后端使用与 Manifest 一致的距离度量语义。

若业务需要 L2 归一化或其他转换，必须把它定义为显式预处理步骤，并记录算法和版本，避免同一数据集被不同配置生成语义不同的索引。

### 8.3 索引后端隔离

```
export interface VectorIndexBuildRequest {
  vectorsPath: string;
  outputPath: string;
  dimension: number;
  metric: "cosine" | "l2" | "ip";
  rowIds: Uint32Array;
  parameters: Record<string, string | number | boolean>;
}

export interface VectorIndexBuildResult {
  indexPath: string;
  indexedCount: number;
  backend: string;
  backendVersion: string;
  parameters: Record<string, string | number | boolean>;
}
```

这段代码是接口设计示例，后续实现需要根据目标索引库的真实 API 调整。若数据集可能超过 \\(2^{32}-1\\) 行，不应使用 `Uint32Array` 表达行 ID，应选择经过验证的 64 位或字符串映射方案。

索引构建完成后，必须通过后端的加载或校验接口重新打开索引，确认维度、计数和度量配置。只检查“索引文件存在且非空”不足以证明索引有效。

## 9. ID 映射文件一致性

沿用 V1.4 的两文件方案：

- `id-map.jsonl`：每行描述一个向量记录的映射；
- `id-map.offsets`：记录每条 JSONL 记录的起始偏移。

### 9.1 必须满足的条件

设映射记录数为 \\(N_v\\)，JSONL 文件长度为 \\(L\\)：

- offsets 条目数为 \\(N_v+1\\)；
- 偏移数组采用无符号 64 位小端序；
- 第一个偏移为 `0`；
- 偏移单调递增或在允许空记录的格式下满足相应严格规则；
- 最后一个偏移为 \\(L\\)；
- 每条映射记录的 `row_id` 必须唯一；
- `row_id` 必须指向有效 SQL 记录；
- 若要求一条 SQL 记录对应一个向量，则不得遗漏记录。

偏移文件大小：

\\[ \operatorname{bytes}=(N_v+1)\times8 \\]

JSONL 的最后一条记录是否包含换行符必须统一。建议每条记录均以 `\n` 结尾，并将该规则写入格式版本。

### 9.2 重复和缺失映射

构建时必须明确选择以下语义之一：

- 一对一：每个 `row_id` 最多一个向量，缺失即报错；
- 部分覆盖：仅部分 SQL 记录具有向量，缺失记录明确记录；
- 一对多：允许同一业务实体有多个向量，但必须通过不同的向量记录 ID 表达，不能重复使用同一个唯一向量行 ID。

V1 推荐一对一，部分覆盖作为显式可选模式；一对多应留到后续版本定义。

## 10. Manifest 规范

Manifest 是 Runtime 判断数据包结构、读取文件和确认兼容性的唯一标准入口。不要让 Runtime 依赖 Builder 的内部目录约定。

### 10.1 示例结构

以下 JSON 为规范草案，具体字段名称应在实现前与 V1.0 API Contract 合并锁定。

```
{
  "format": "weisql",
  "formatVersion": "1.0",
  "dataset": {
    "id": "docs-dataset",
    "version": "2026-10-30.1",
    "createdAt": "2026-10-30T00:00:00Z"
  },
  "tables": [
    {
      "name": "documents",
      "schemaPath": "metadata/schema.json",
      "rowCount": 200000,
      "files": [
        {
          "path": "data/part-00000.parquet",
          "rowCount": 100000,
          "rowIdStart": 0,
          "rowIdEndExclusive": 100000,
          "sizeBytes": 73400320,
          "sha256": "<64位十六进制SHA-256>"
        },
        {
          "path": "data/part-00001.parquet",
          "rowCount": 100000,
          "rowIdStart": 100000,
          "rowIdEndExclusive": 200000,
          "sizeBytes": 73400320,
          "sha256": "<64位十六进制SHA-256>"
        }
      ]
    }
  ],
  "vectorCollections": [
    {
      "name": "document-embedding",
      "table": "documents",
      "dimension": 768,
      "dtype": "float32",
      "metric": "cosine",
      "vectorCount": 200000,
      "vectorsPath": "vectors/document-embedding/vectors.f32",
      "idMapPath": "vectors/document-embedding/id-map.jsonl",
      "idMapOffsetsPath": "vectors/document-embedding/id-map.offsets",
      "index": {
        "backend": "usearch",
        "backendVersion": "<validated-version>",
        "path": "indexes/document-embedding/usearch.index",
        "metaPath": "indexes/document-embedding/index-meta.json"
      }
    }
  ],
  "files": [
    {
      "path": "metadata/schema.json",
      "sizeBytes": 4096,
      "sha256": "<64位十六进制SHA-256>"
    }
  ]
}
```

注意：

1. 示例中的 SHA-256 和索引版本是占位符，正式产物不得保留占位符。
2. 生产 Manifest 应覆盖全部需要验证的文件，包括向量文件、ID 映射、索引文件、Schema 和索引元数据。
3. 不建议把所有文件摘要只存到 `files` 数组、却在 `tables` 和 `vectorCollections` 中重复维护互相矛盾的摘要。正式 Schema 应定义唯一权威文件登记表，并由引用字段指向该登记表。
4. `formatVersion` 描述数据包格式；`dataset.version` 描述数据内容版本。两者不能混为一谈。
5. 时间戳应采用 RFC 3339 / ISO 8601 UTC 格式。

### 10.2 Manifest 生成顺序

推荐顺序：

1. 完成所有数据文件；
2. 完成索引和索引元数据；
3. 计算全部文件长度和 SHA-256；
4. 执行完整性与一致性验证；
5. 生成 Manifest；
6. 对 Manifest 自身执行 Schema 校验；
7. 写入构建报告；
8. 发布。

Manifest 不应包含自身 SHA-256，除非另行定义外部签名或包级校验文件，以避免循环依赖。

## 11. 发布前验证器

`package-validator` 是发布前的强制门禁，不允许用“构建步骤都返回成功”替代它。

### 11.1 验证分层

| 层级     | 检查项                         | 失败是否阻止发布 |
| ------ | --------------------------- | -------- |
| L1：结构  | Manifest Schema、必填字段、格式版本   | 是        |
| L2：文件  | 文件存在、路径安全、长度、SHA-256        | 是        |
| L3：数据  | Parquet 可读取、Schema、行数、分片连续性 | 是        |
| L4：向量  | 维度、元素有限性、字节长度、度量配置          | 是        |
| L5：映射  | offsets 长度、边界、重复 ID、行范围     | 是        |
| L6：索引  | 可重新加载、维度、记录数、后端版本           | 是        |
| L7：跨文件 | SQL 行数、向量计数、映射和索引记录一致       | 是        |
| L8：运行时 | 用正式 Runtime 打开并执行代表性查询      | 是        |
| L9：性能  | 加载时间、查询延迟、内存、Recall\@K      | 按发布配置    |

### 11.2 运行时冒烟测试

每个待发布数据包至少执行：

- 打开 Manifest；
- 加载 SQL Adapter；
- 执行简单 `SELECT`；
- 执行分页或流式读取；
- 执行向量 top-K；
- 检查结果中的 `row_id` 是否能解析到 SQL 记录；
- 执行过滤和混合检索（若该包声明支持）；
- 调用 `close()`；
- 验证关闭后的查询按契约失败。

向量结果正确返回但无法关联回业务记录，仍应判定数据包无效。

### 11.3 完整校验与快速校验

建议区分两种模式：

- `full`：重新计算所有文件 SHA-256，重新读取数据并验证跨文件一致性；正式发布默认使用。
- `fast`：仅用于本地开发阶段，允许依赖本次构建过程中保存的可信统计，但不得作为正式发布的唯一门禁。

“可信统计”只适用于受控的同一构建流程；从外部复制、下载或缓存恢复的产物必须重新验证。

## 12. 原子发布与不可变版本

### 12.1 推荐发布目录

```
releases/
├── docs-dataset/
│   ├── 2026-10-30.1/
│   │   ├── manifest.json
│   │   ├── data/
│   │   ├── vectors/
│   │   └── indexes/
│   └── 2026-10-30.2/
│       ├── manifest.json
│       ├── data/
│       ├── vectors/
│       └── indexes/
└── channels/
    └── stable.json
```

发布版本目录一旦成功发布，应视为不可变。更新数据时生成新版本，而不是覆盖旧版本中的文件。

### 12.2 发布步骤

1. 在目标发布文件系统或临时区域构建完整包；
2. 执行正式验证；
3. 确保最终版本号没有被占用；
4. 将整个已验证目录移动到新版本路径；
5. 在目标环境支持时，通过同一文件系统内的原子重命名完成目录发布；
6. 更新可选版本指针；
7. 验证指针指向的新版本可被 Runtime 打开；
8. 输出发布报告。

原子性边界必须明确。 POSIX 文件系统中同一文件系统内的适当重命名通常可以提供原子可见性，但对象存储、跨文件系统移动、Netlify 静态部署和多文件上传不能直接假设具备相同保证。

对于对象存储或静态托管：

- 先上传不可变版本目录；
- 上传完成后验证全部文件；
- 最后更新一个很小的版本指针或索引文件；
- Runtime 优先读取已解析出的不可变版本 URL；
- 版本指针更新不等于所有 CDN 节点同时刷新，因此应允许短暂缓存延迟，并避免同一路径下覆盖文件。

### 12.3 回滚

回滚不是重写数据文件，而是将指针切回已知有效的旧版本。

回滚必须确认：

- 旧版本仍然存在；
- 旧版本的 Manifest 和必要文件仍可读取；
- 旧版本仍与当前 Runtime 兼容；
- CDN 缓存策略不会把新 Manifest 与旧数据文件混用。

因此，版本目录应使用不可变 URL，例如：

```
/datasets/docs-dataset/2026-10-30.1/manifest.json
```

而不是让长期缓存的 `/datasets/latest/data.parquet` 被覆盖。

## 13. 失败恢复、幂等性与取消

### 13.1 构建日志

每次构建应有唯一 `buildId`，日志至少包含：

- 构建器版本；
- 配置摘要；
- 输入文件路径、大小和摘要；
- 当前阶段；
- 阶段开始、结束时间；
- 处理记录数；
- 已生成文件清单；
- 验证结果；
- 错误代码和可读错误信息；
- 是否可重试。

日志不得泄漏 API Key、凭据、敏感原始文本或用户数据内容。

### 13.2 幂等性原则

相同输入、相同配置和相同工具链版本应尽可能生成语义相同的数据包，但不应默认要求所有二进制文件完全逐字节相同：Parquet 元数据时间戳、索引构建随机性或依赖版本都可能影响字节结果。

建议定义两层摘要：

- 输入与配置摘要：判断是否为同一逻辑构建；
- 产物摘要：记录实际输出文件的 SHA-256。

如果索引算法具有随机性，应记录随机种子和后端版本，并通过结果正确性、Recall 和查询行为判断语义一致性。

### 13.3 恢复规则

| 失败位置       | 推荐恢复策略                      |
| ---------- | --------------------------- |
| 输入校验       | 修正配置后重新运行                   |
| Parquet 分片 | 仅当分片有独立校验记录且输入摘要一致时，才允许复用   |
| 向量文件       | 验证字节长度、行数、输入摘要后决定复用         |
| ANN 索引     | 默认重建；若复用，必须验证后端版本、参数和输入向量摘要 |
| Manifest   | 重新生成，不能依赖旧清单中的陈旧文件          |
| 发布         | 检查最终目录与指针状态，避免重复发布或覆盖版本     |
| 用户取消       | 停止接收新任务，尽力中止当前任务并清理 staging |

### 13.4 清理策略

- 失败 staging 目录不得进入正式版本目录。
- 默认保留最近若干次失败构建的日志；数据内容可按隐私策略清理。
- 正式版本的清理应与 Runtime 引用和 CDN 缓存策略协调。
- 不得删除当前版本或回滚目标版本。
- 对跨平台目录锁、进程崩溃和并发发布应单独测试，不能仅依赖进程内锁。

## 14. 安全规范

### 14.1 路径安全

所有 Manifest 路径均应视为不可信输入。必须拒绝：

- 绝对路径；
- `.`、`..` 等路径穿越段；
- 反斜杠、NUL；
- URL Scheme；
- 查询串和片段；
- 编码后绕过检查的路径；
- 规范化后逃逸数据包根目录的路径。

Node.js 还必须防范符号链接逃逸、路径竞争和 TOCTOU 问题。仅使用 `path.join()` 或字符串前缀检查不构成充分的安全边界。

浏览器端则应限制 Manifest 解析出的资源 URL，避免数据包通过恶意路径访问任意站点或本地敏感资源。

### 14.2 哈希与信任

SHA-256 用于检测文件与 Manifest 声明不一致，不等于证明数据包由可信发布者发布。

V1 可先使用完整性校验；后续若需要发布者认证，再增加独立签名机制，定义可信公钥分发、签名覆盖范围、密钥轮换和撤销策略。

### 14.3 外部向量与索引文件

- 不应反序列化未经验证的索引文件并直接视其为可信。
- 应使用受支持的后端版本和官方加载接口。
- 对异常大维度、异常记录数和异常文件长度设置上限。
- 对不可信数据包限制内存、CPU、并发和解压规模。
- 错误报告中不得直接拼接未经清理的控制字符或敏感路径。

## 16. 测试规范

### 16.1 单元测试

- Schema 校验、主键重复检测、空值策略；
- Parquet 分片区间生成；
- Float32 文件长度和有限值检查；
- ID 映射唯一性和偏移边界；
- Manifest 引用解析；
- 路径穿越拒绝；
- 文件摘要计算；
- 发布版本冲突检测；
- 状态机非法转换拒绝。

### 16.2 集成测试

| 场景                       | 预期                    |
| ------------------------ | --------------------- |
| CSV → Parquet → SQL 查询   | 行数、字段值和类型符合预期         |
| JSONL + Embedding → 向量索引 | 映射正确，top-K 结果可关联到 SQL |
| 随机打乱向量输入顺序               | 通过显式 ID 映射后仍能正确关联     |
| 删除一个 Parquet 文件          | 完整验证失败                |
| 修改一个向量字节                 | SHA-256 校验失败          |
| 修改 ID offsets            | 映射验证失败                |
| 索引维度不匹配                  | 索引验证失败                |
| 发布过程中进程退出                | 不出现可见的半成品正式版本         |
| 新版本发布失败                  | 旧版本仍可读取               |
| 同版本并发发布                  | 不覆盖已有版本，返回明确冲突        |
| Runtime 打开并关闭            | 查询成功，关闭后按契约拒绝操作       |
| Range 不受服务器支持            | 资源层按 V1.3 规范报错，不静默误读  |

### 16.3 性能测试

建议至少测试：

- 10 万条记录：开发基线；
- 50 万条记录：中型数据包；
- 100 万条向量：首版性能验收目标。

测试必须记录机器、操作系统、Node.js 版本、浏览器版本、CPU、内存、存储类型、索引后端和参数。测试报告区分冷缓存与热缓存。

至少报告：

- 构建总耗时和分阶段耗时；
- Parquet 总大小；
- 向量文件大小；
- ANN 索引大小；
- 峰值内存；
- 查询 P50/P95；
- Recall\@K；
- Runtime 打开耗时；
- 资源请求次数、缓存命中率和 Range 行为。

不能只展示平均延迟，也不能把单次本地测试当成普遍性能承诺。

## 17. 首版验收标准

以下条件全部满足后，才可将 Builder 标记为 V1 可发布：

- 能从受支持的源格式生成完整数据包。
- SQL Schema、Parquet 行数和行号区间一致。
- 向量维度、数值和距离度量符合规范。
- 每个向量记录都能映射到有效 SQL 记录。
- 索引可重新加载，元数据与实际文件一致。
- Manifest 对所有必要文件的引用正确。
- 完整 SHA-256 验证通过。
- 正式 Runtime 能打开数据包并执行 SQL、向量查询。
- 关闭、取消和失败状态满足契约。
- 发布失败不会覆盖或破坏已有版本。
- 旧版本回滚流程通过测试。
- 路径穿越、损坏文件和错误映射测试通过。
- 性能测试包含真实环境信息和可重复步骤。
- 构建产物、日志和配置中没有泄漏凭据。
