# WeiSQL AI 产品需求规格说明书 V2.0

文档类型：产品需求文档（PRD） · 状态：需求评审稿 · 阶段：需求定义，不进入编码

## 一、产品定位

WeiSQL AI 是一个面向 AI 应用、知识库和静态数据应用的 TypeScript 数据查询 SDK。

它将结构化数据、向量数据和可选的全文检索能力封装为统一的数据包与查询接口，让开发者能够在 Node.js 或浏览器中访问数据，并将其部署到静态网站、CDN 或 Netlify 等托管环境。

## 产品核心价值

结构化查询

通过 SQL 查询数据，无需为每个只读数据集单独搭建数据库服务。

向量与混合检索

支持语义向量搜索、结构化条件过滤，以及后续可选的全文检索和结果融合。

可移植的数据包

将数据、Manifest、向量映射和可选索引组织为有版本、可验证的数据发布单元。

多环境运行

统一 Node.js 与浏览器的公共 API，支持静态托管和按需读取资源。

### 1.1 产品目标

1. 降低 AI 应用访问结构化数据与向量数据的开发成本。
2. 支持数据与应用分离部署，避免只读场景必须维护独立数据库服务。
3. 统一 SQL、向量搜索和混合检索的使用方式。
4. 通过数据包校验和稳定的错误处理提升可靠性。
5. 为未来的 Rust 核心算法、WASM 和高性能检索适配器预留扩展空间。

### 1.2 非目标

首版不承诺以下能力：

- 在线数据写入、事务与多用户同步。
- 完整的数据库服务器替代能力。
- 任意格式数据的自动转换。
- 所有浏览器和静态托管环境都具有相同的性能。
- 所有向量索引后端都能达到相同的搜索精度和延迟。
- 自动生成或自动训练 Embedding 模型。
- 自动提供 LLM 推理服务。

## 二、目标用户与典型场景

| 用户类型     | 主要问题                      | 使用场景             | 期望结果           |
| -------- | ------------------------- | ---------------- | -------------- |
| AI 应用开发者 | RAG 应用需要管理文档元数据和向量        | 本地或静态部署的知识库      | 统一查询结构化数据和向量   |
| 前端开发者    | 浏览器应用需要查询数据，但不希望自建 API 服务 | 文档站、产品目录、交互式数据网站 | 静态部署并按需读取数据    |
| 数据工程师    | 数据转换后缺少统一交付格式             | 数据集加工与发布         | 构建可验证、可版本化的数据包 |
| 独立开发者    | 希望低运维部署小型数据应用             | 个人项目、Demo、工具网站   | 降低服务器依赖        |
| 企业研发团队   | 多个应用重复实现数据访问层             | 内部知识检索与只读数据应用    | 统一 SDK 与数据交付规范 |

### 2.1 核心用户故事

- 作为开发者，我希望将数据构建成一个数据包，以便独立发布和更新。
- 作为前端开发者，我希望直接在浏览器查询数据，而不必为每个查询开发后端 API。
- 作为 AI 开发者，我希望按向量相似度查找内容，并结合业务字段过滤。
- 作为数据维护者，我希望发现文件损坏、版本不兼容和资源缺失，而不是得到错误结果。
- 作为应用开发者，我希望在 Node.js 与浏览器中使用一致的公共接口。
- 作为维护者，我希望通过自动测试发现 API 变更导致的兼容性问题。

## 三、产品功能范围

建议按以下优先级管理功能。

### P0

首版必需

基础数据包与 Runtime

Manifest 解析、数据包打开、资源读取、SQL 查询、向量精确搜索、统一错误处理、关闭与资源释放。

### P1

首版增强

完整数据构建与混合检索

Builder、ANN 索引适配、结构化过滤、分页、浏览器 Range 读取、完整性校验和发布验证。

### P2

后续版本

高级检索与扩展

全文检索、结果融合、流式查询、Rust/WASM 算法复用、单文件数据包等。

这里的优先级是本次需求评审建议，尤其是 ANN、全文检索和流式查询是否进入首个正式版本，需要在需求确认时锁定。

## 五、非功能性需求

### 5.1 正确性

- 精确向量搜索必须与参考算法一致。
- SQL 查询必须遵守明确的参数绑定和只读规则。
- Manifest 中的文件引用、大小和哈希必须可验证。
- 错误不能被静默转换成空结果。
- 同一公共操作在不同环境中应遵守同一语义。

### 5.2 性能与内存

首版以可测量性为前提，不预先承诺尚未验证的延迟指标。

基准规模建议采用：

| 基准等级 | 数据规模    | 维度  |
| ---- | ------- | --- |
| 小型   | 100K 向量 | 768 |
| 中型   | 500K 向量 | 768 |
| 大型   | 1M 向量   | 768 |

必须分别记录构建时间、打开时间、查询 P50/P95、索引大小、峰值内存与 ANN Recall\@K。

### 5.3 安全与完整性

- 禁止数据包路径逃逸。
- 校验文件哈希时使用实际读取的字节。
- 避免将用户输入直接拼接到 SQL。
- 避免在生产错误信息中泄露密钥、绝对路径和敏感参数。
- 区分数据完整性校验和发布者身份认证。
- 缓存必须正确区分数据集版本。
- 数据发布失败不得留下被误认为有效的半成品。

### 5.4 可移植性

- 公共 API 使用 TypeScript 类型。
- Node.js 与浏览器有独立运行时入口。
- 公共接口不暴露引擎内部类型。
- 不支持的环境能力必须可检测、可解释。

## 六、核心业务流程

### 6.1 数据生产者流程

```
原始数据
   ↓
数据转换与 Schema 检查
   ↓
生成 Parquet 与向量文件
   ↓
建立业务 ID 映射
   ↓
生成可选 ANN 索引
   ↓
生成 Manifest
   ↓
完整性验证与查询冒烟测试
   ↓
发布不可变版本目录
```

### 6.2 数据消费者流程

```
选择数据包
   ↓
open()
   ↓
检查 capabilities
   ↓
SQL / Vector Search / Hybrid Search
   ↓
读取与查询结果
   ↓
close()
```

### 6.3 AI/RAG 应用流程

```
用户问题
   ↓
由应用侧生成 Query Embedding
   ↓
WeiSQL AI 执行向量检索
   ↓
按业务字段过滤
   ↓
返回文档 ID、距离与元数据
   ↓
应用侧获取内容并调用 LLM
```

这里需要明确一个边界：WeiSQL AI 负责数据访问和检索，不负责首版的 Embedding 模型推理、LLM 调用、提示词编排或答案生成。

## 七、首版验收标准

| 验收项     | 必须满足的条件                   |
| ------- | ------------------------- |
| 数据包     | 可构建、校验并被 Runtime 打开       |
| SQL     | 支持基本查询与参数绑定               |
| 向量搜索    | 精确搜索与距离定义正确               |
| ID 映射   | 可从向量行号映射到业务 ID            |
| 数据完整性   | 能发现损坏或不匹配的资源              |
| Node.js | 主要公共 API 集成测试通过           |
| 浏览器     | 在声明支持的 HTTP(S) 环境中验证读取与查询 |
| 生命周期    | `close()`、取消与错误行为符合契约     |
| API 稳定性 | 公共类型与错误码可自动检查             |
| 发布      | 关键测试失败时不能发布正式版本           |

性能目标、ANN 最低 Recall\@K、支持的 Node.js 版本、浏览器最低版本和单次查询最大资源占用，应在具体实现和基准验证后再设定正式数值。

## 八、已采纳的产品决策

以下决策结合本 PRD 的产品目标与当前仓库已经验证的能力确定。它们用于约束后续需求评审，不代表所有外部环境、性能指标或发布流程均已完成最终验收。

### 8.1 首版主要运行环境

Node.js 与浏览器均属于正式目标环境。公共查询语义、错误分类和数据包格式应尽可能一致；引擎能力、参数类型、取消能力和性能差异必须通过 `capabilities` 与兼容性文档明确披露。

### 8.2 ANN 向量索引

TypeScript 精确搜索是正确性基线，ANN 是可选增强能力。ANN 结果必须标记为近似结果，并以精确搜索计算 Recall@K；不得因仓库已有 ANN 适配器而把特定召回率或延迟写成普遍产品承诺。

### 8.3 数据包构建工具

Builder API 与 CLI 均作为产品入口：API 服务于自动化集成，CLI 服务于构建、校验、检查、打包和发布流程。两者必须共享数据格式、校验规则与错误语义，不能形成两套不兼容的构建结果。

### 8.4 全文检索

全文检索属于可选增强能力，不是所有数据包和 Runtime 的必备能力。数据包未声明全文索引或当前 Runtime 未加载对应实现时，能力查询必须返回不可用，调用不得静默降级。

### 8.5 可视化产品边界

SDK、Runtime 与 Builder 是核心交付物。Playground 用于演示和端到端验收，可以随核心能力持续完善；桌面客户端仍属于探索性方向，不作为首版正式交付物，也不得反向约束核心 API。

## 九、需求冻结与变更规则

1. 本 PRD 是产品范围、用户价值、优先级和验收目标的需求基线。
2. 已实现能力不自动成为永久必需能力；是否属于核心产品范围以本 PRD 的 P0/P1/P2 定义为准。
3. 技术文档不得擅自扩大产品承诺，尤其不得把单机基准、合成数据召回率或特定浏览器结果推广为普遍保证。
4. 需求变化必须说明受影响的用户场景、优先级、兼容性、数据格式和验收用例。
5. Manifest、公共 API、错误码或距离语义发生不兼容变化时，必须经过单独评审并提供迁移策略。
6. 在进入下一轮架构或编码工作前，应先将新增任务映射到本 PRD 的需求 ID；无法映射的工作需先说明其产品价值和范围。

## 十、下一阶段

下一步应基于本 PRD 建立“需求 ID → 当前实现 → 自动化测试 → 文档 → 未验证项”的追踪矩阵，识别已经交付、部分交付和仍待验证的项目。完成追踪后，再决定哪些工程任务真正属于下一阶段，避免按旧计划重复实现已经存在的能力。
