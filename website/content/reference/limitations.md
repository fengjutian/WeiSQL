本页只列“现在还不能依赖”的部分。能做什么见 [能力矩阵](/reference/capabilities)；本页回答的是“哪里会出问题、为什么、怎么绕开”。

## 状态说明

| 状态 | 含义 | 你该怎么处理 |
| --- | --- | --- |
| 未验证 | 实现存在，但没有在目标场景测量 | 上线前自己测，不要引用仓库数字外推 |
| 未实现 | 没有可用实现 | 不要基于它做设计 |
| 明确不做 | 有意排除在范围外 | 换方案，不要等排期 |

“测试通过”不等于“生产就绪”。下面的条目大多是测量或决策缺口，而不是代码 bug。

## 外部条件阻塞

这些项需要仓库之外的资源才能推进，当前没有时间表。

| 项 | 阻塞原因 | 影响 | 缓解方式 |
| --- | --- | --- | --- |
| npm 发布 | 缺少组织与访问令牌；许可证已定为 Apache-2.0 | 五个包只能从源码构建，不能 `npm install` | 从仓库 `npm install` 后本地链接 |
| 真实数据集 Recall@K | 缺少真实 embedding 语料 | ANN 只有合成数据数字（0.385–0.740） | 用你自己的数据跑 `npm run bench -- --ann` |
| 多机与冷缓存基准 | 需要第二台机器与清缓存手段 | 现有延迟都是单机热缓存 | 视为量级参考，不做 SLA |
| 真实 CDN / CORS 验收 | 需要实际部署环境 | Range、CORS、缓存与重定向行为未验证 | 部署后先用 `probe:browser` 的同类检查验证 |
| 浏览器内大表与 34 MB 首载 | 需要真实浏览器与网络测量，且受设备差异影响 | 浏览器 SQL 冷启动与内存没有数字 | 首屏不要依赖 SQL；按需加载 |

其中“真实数据集 Recall@K”是当前最大的未知：Node 端性能结论不能外推到 WASM，合成数据结论也不能外推到你的语料。

## 设计未定

这些项不是做不了，而是方案还没定，或定了但没实现。

| 项 | 当前状态 | 影响 |
| --- | --- | --- |
| SQL 结果流式返回 | `maxRows` 能硬失败并让引擎提前停止，结果仍是一次性数组 | 大结果集只能拒绝，不能边读边处理 |
| 浏览器 OPFS 持久化 | 未实现 | 每次打开都要重新加载 WASM 与物化表 |
| ANN 过滤的完整性 | 只有显式后过滤，结果可能少于 `topK`，靠 `diagnostics.postFiltered` 自曝 | 过滤 + ANN 不能声明严格 Top-K |
| 索引格式的主版本内变更 | 只校验 `engine` 与向量数量，不校验 USearch 版本 | 引擎小版本改变索引布局时可能读错 |
| 融合质量 | 只测了 RRF `k` 的稳定性，没有相关性标注 | 无法回答“哪个 `k` 排序更好” |
| `.wsql` 压缩协商 | 目前只有 gzip，brotli 需要新版本号 | 压缩率与解压成本无法按客户端协商 |
| JSON 等值过滤 | 明确拒绝，错误带 `hint` | 需要 JSON 谓词只能走 `db.sql()` 的 `json_extract` |
| 时间戳与嵌套列推断 | CSV/JSON 转换只覆盖标量 | 源数据要先自己整理成 Parquet |
| 中文分词 | CJK 逐字，精度换可预测性 | 中文召回偏字面，词级语义弱 |
| 非只读 CTE 的形态 | CTE 后不是只读动词一律拒绝，无法识别的形态 fail-closed | 个别合法只读写法会被误拒 |
| 浏览器 SQL 参数类型 | JSON 绑定，`Date`、二进制、超范围 `bigint` 拒绝 | 时间过滤需传 ISO 字符串 |
| 浏览器 SQL 扩展分发 | 必须同源自托管，`extensions.duckdb.org` 无 CORS 头 | 部署多一步，且要与 WASM 核心版本对齐 |
| WASM 与 TypeScript/Rust 黄金数据对照 | 未实现 | 跨实现一致性靠 `probe:parity`，不是全量黄金集 |

## 明确不做

这些是有意排除的，不是待办。

| 项 | 原因 |
| --- | --- |
| 写入、事务、多用户并发 | 只读是产品边界；数据包是不可变发布单元 |
| 自研 SQL 引擎或优化器 | 复用 DuckDB，SDK 只做注入与边界 |
| 自研完整 ANN 引擎 | 复用 USearch；Rust 只保留精确 Cosine 对照基线 |
| 把 API Key、私有 prompt、客户数据打进包 | 静态包默认可被公开下载 |
| 浏览器与 Node 的完整 SQL 方言对等承诺 | 两个引擎构建能力不同，只承诺对照集内的语义一致 |
| 百万级向量的固定延迟或内存承诺 | 没有对应规模的真实测量 |
| ANN 结果的精确性声明 | ANN 必须 `exact: false`；后过滤不保证完整 |
| COI 多线程构建 | 试过：加载 parquet 扩展直接 `LinkError`（扩展声明非共享内存） |
| `.wsql` 加密 | 加密会改变“静态、只读、可公开校验”的模型；访问控制交给托管层 |
| 替代通用数据库 | 只读静态包不适合事务型存储，也不是 SQLite 的通用替代品 |

## 容易被忽略的边界

即使功能“已实现”，下面这些限制仍然存在：

- **SHA-256 不证明发布者身份**。它只证明内容与 Manifest 一致；来源真实性要靠签名与固定 `keyId`。
- **完整性校验默认关闭**。`verifyChecksums` 默认 `none`，只做 L1/L2；要防同长度篡改必须用 `all`。
- **L4 不校验可空性**。`read_parquet` 不保留 `NOT NULL`，`DESCRIBE` 对非空列也返回 `YES`。
- **`DECIMAL` 有精度天花板**。两端都转成 `number`，超过 15 位有效数字会丢精度。
- **`lazy` 模式保留外部文件访问**。它能挡写入，挡不住读取，只适合应用作者编写的 SQL。
- **缓存不跨发布版本**。`setPublicationVersion()` 换版本即清空，不会混用新旧资源块。
- **流式容器遇到压缩条目要整条取回**。Range 语义在 gzip 条目上无法直接切片。
- **浏览器取消不回收资源**。调用方不再等待，但引擎可能把查询跑完。

## 如何自查

不要只读文档判断，直接跑：

```bash
npx weisql validate ./my-package --json --mode all   # L1/L2/L3
npx weisql validate ./my-package --l4                # 额外核对 Parquet
npm run bench -- --ann                               # 你自己的召回与延迟
npm run probe:parity                                 # 两端结果是否一致
```

如果某项能力没有出现在 [能力矩阵](/reference/capabilities) 里，就按“未验证”处理。

## 为什么会有这些限制

限制的来源不同，应对方式也不同：

- **产品前提**：只读、不可变、无服务端。写入与事务不是“还没做”，而是不在范围内，等它没有意义。
- **跨环境差异**：浏览器与 Node 的 SQL 引擎是两个构建产物，只读边界、参数与取消强度天然不同。这是引擎事实，不是 SDK 抽象失败。
- **测量缺口**：真实语料上的 ANN 召回、真实 CDN 的 Range/CORS、多机基准。代码可能正确，但没有证据就不能承诺。
- **安全取舍**：`lazy` 模式保留外部文件访问是有意为之；JSON 等值过滤拒绝而不是猜规范化形式；`maxRows` 超限硬失败而不是截断。
- **上游能力**：DuckDB-Wasm 不暴露 `StatementType`；`extensions.duckdb.org` 无 CORS 头；COI 运行时与 parquet 扩展的内存模型不兼容。

区分这几类很重要：最后一类要等上游，倒数第二类需要重新讨论取舍，前两类则不该被反复追问。

## 采用前的检查清单

- [ ] 数据能否公开下载？包里的每个字节都可能被任何人拿到。
- [ ] 更新频率是否低于发布频率？每次内容变化都要重建并重新发布。
- [ ] 是否需要写入、事务或多租户隔离？需要就换方案。
- [ ] 是否接受浏览器端约 34 MB WASM 首载与 SQL 冷启动？
- [ ] ANN 是否用你自己的语料测过 Recall@K？
- [ ] 静态托管的 Range 与 CORS 是否已验证？
- [ ] 是否需要 `Date` 或二进制参数？需要就优先选 Node。
- [ ] 终端用户能否输入 SQL？能，就只允许 `memory` 模式。
- [ ] 是否开启 `verifyChecksums: "all"`？不开就发现不了同长度篡改。

## 当前瓶颈在哪

仓库的开发顺序里，第 7 步是明确的瓶颈：**真实 embedding 数据集的 Recall@K、多机基准复现、静态 CDN/CORS 验收**。这三项都依赖仓库之外的资源，也都直接决定“能不能对外承诺”。

在此之前，任何关于百万级向量延迟、浏览器内存、ANN 召回率或 CDN 随机访问效率的说法都只是推测。现有的 100k × 128 合成数据数字可以说明量级，但不能替代你的场景。

## 把“未验证”变成“已验证”

- **真实语料**：把目标 embedding 写成 Parquet 与 f32，跑 `npm run bench -- --ann`，连同数据分布、规模一起记录 Recall@K；
- **CDN**：部署后检查 `206`、`Content-Range`、CORS 暴露头与缓存行为，再跑一遍浏览器探针；
- **多机**：在第二台机器与冷缓存下重复同一基准，报告区间而不是单点；
- **浏览器大表**：在目标设备上测 `open()`、物化内存与首载时间，不要用 Node 里的 WASM 数字替代。

这四件事没有一件能靠读代码完成。

## 限制会变

每完成一项测量或上游能力发生变化，这张表就应更新。具体状态以 [能力矩阵](/reference/capabilities) 为准；本页只解释原因与影响，不承担排期。
