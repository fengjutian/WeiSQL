## 一句话

<Module>

WeiSQL 的核心设计只有一句话：**把“数据库服务”换成“可版本化的静态数据包 + 一层只读 Runtime”**。理解这一点，后面的 Adapter、缓存、完整性校验都是它的推论。

<Callout title="两个方向都是单向依赖">
  上层只依赖接口，不依赖具体引擎；Adapter 通过 `open({ sqlAdapter, vectorAdapter })`
  注入，能力通过 `capabilities()` 如实上报。SDK 本身没有 DuckDB、USearch 的运行时依赖。
</Callout>

</Module>

## 2. 一次向量查询

<Module>

以默认的 `exact-filter-first` 策略为例，一次 `vector.search()` 会经过六步：

<FlowSteps
  steps={[
    {
      title: "校验参数",
      desc: "维度、topK、filter 列是否在 Manifest 中声明；非法输入在读取前失败。",
      code: "VECTOR_DIMENSION_MISMATCH",
    },
    {
      title: "求出允许行",
      desc: "有 filter 时编译为参数绑定 SQL，由 SqlAdapter 返回完整业务 ID 集合。",
      code: "exact-filter-first",
    },
    {
      title: "ID → 行号",
      desc: "优先使用持久化 id→row 索引；没有索引时扫描 ID Map。",
      code: "idIndex → row",
    },
    {
      title: "读取向量块",
      desc: "连续行合并成 Range 读取，按 Float32 LE 解码；窄过滤只读允许行。",
      code: "ByteRange",
    },
    {
      title: "距离与 Top-K",
      desc: "逐条计算距离（Cosine / L2 / IP），用固定容量最大堆维护候选。",
      code: "O(N log K)",
    },
    {
      title: "解析业务 ID",
      desc: "只对最终 Top-K 读取 ID Map，返回 hits 与 diagnostics。",
      code: "exact: true",
    },
  ]}
/>

<Callout title="过滤发生在 Top-K 之前">
  所以结果仍是过滤子集上的严格最近 K，`exact: true` 才站得住。分块读取降低峰值内存，
  但不减少总 I/O 与计算量；精确检索依旧是 O(N) 扫描，这是 V1 的明确取舍。
</Callout>

`vector-first` 则先取有界候选窗口，再用 SQL 过滤；只有窗口覆盖整个集合时才可能
`exact: true`（靠穷尽，而非构造）。它省掉的是全量 ID Map 扫描，不是向量扫描。

</Module>

Adapter 打开时会从 `ResourceReader` 读表字节、按 Manifest 比对列定义（L4），再把表加载到引擎。Node 默认 `memory` 模式，物化后关闭外部文件访问；`lazy` 保留外部访问，只适合由应用作者编写 SQL 的场景。

</Module>

## 4. 信任边界

<Module>

Manifest 和所有远程资源都按**不可信输入**处理：

<CardGrid columns={2}>
  <DocCard title="路径" index="01">
    规范化后再 I/O；拒绝绝对路径、`..`、反斜杠、URL scheme 与重复规范路径。
  </DocCard>
  <DocCard title="传输" index="02">
    HTTP 只接受 `206` 与匹配的 `Content-Range`；短读、超长、取消都不进入缓存。
  </DocCard>
  <DocCard title="内容" index="03">
    L3 用声明尺寸与 SHA-256 检测损坏；签名用于发布者身份，二者不是一回事。
  </DocCard>
  <DocCard title="SQL" index="04">
    只读语句分类、参数绑定、单语句；`memory` 模式关闭外部文件访问。
  </DocCard>
  <DocCard title="数据本身" index="05">
    静态包默认可被下载，不得放入密钥、令牌或私密数据。
  </DocCard>
  <DocCard title="发布版本" index="06">
    缓存键包含发布版本身份；换版本即失效，避免新旧资源块混用。
  </DocCard>
</CardGrid>

<Callout tone="amber" title="SHA-256 不等于可信发布者">
  SHA-256 只证明“内容与 Manifest 一致”，不证明“发布者可信”。后者要靠 Ed25519
  签名与信任固定。
</Callout>

</Module>

## 5. 三种部署形态

<Module>

<CardGrid columns={3}>
  <DocCard title="目录 + CDN" tag="推荐">
    每个资源独立 HTTP Range；资源多、按需读取、可缓存。需要正确配置 Range 与 CORS。
  </DocCard>
  <DocCard title="单文件 .wsql" tag="单对象">
    整包下载，或流式只读头部再按文件 Range；适合原子替换与单对象发布。
  </DocCard>
  <DocCard title="Node 本地目录" tag="构建期">
    文件句柄加精确偏移，适合构建、测试与离线工具；需要包根 containment。
  </DocCard>
</CardGrid>

三种形态对上层 API 完全一致，因为它们都实现同一个 `ResourceReader` 契约。

</Module>

## 6. 设计原则

<Module>

<CardGrid columns={2}>
  <DocCard title="显式失败" index="01">
    没有 Reader 返回 `INDEX_NOT_FOUND`，没有 SQL Adapter 返回 `SQL_UNSUPPORTED`，不返回空数组假装成功。
  </DocCard>
  <DocCard title="引擎可替换" index="02">
    Adapter 注入，SDK 零引擎依赖；浏览器与 Node 可以选不同实现，能力差异用 `capabilities()` 暴露。
  </DocCard>
  <DocCard title="精确优先" index="03">
    ANN 必须自报 `exact: false`；后过滤必须自报 `postFiltered: true`。
  </DocCard>
  <DocCard title="测量先于承诺" index="04">
    基准装置是测量设备，不是性能承诺；召回数字必须连同数据分布一起报告。
  </DocCard>
  <DocCard title="发布不可变" index="05">
    缓存按发布版本身份隔离；换版本即失效，避免新旧资源混用。
  </DocCard>
  <DocCard title="只读是产品边界" index="06">
    没有写入、事务与锁；需要这些能力时应换方案，而不是等排期。
  </DocCard>
</CardGrid>

</Module>

## 7. 为什么还有一个 Rust crate

<Module>

<Callout tone="amber" title="对照基线，不是生产引擎">
  `crates/vector-benchmark` 是确定性精确 Cosine 基线，用于对照 TypeScript
  实现的正确性与性能，不进入运行时。它的存在是为了让“TS 算得对不对”有一个独立参照。
</Callout>

</Module>
