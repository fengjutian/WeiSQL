## 数据包

V1 的逻辑布局是固定的：

```text
weisql-package/
├── manifest.json
├── data/
│   └── documents.parquet
├── vectors/
│   ├── embeddings.f32
│   ├── id-map.jsonl
│   └── id-map.offsets
├── indexes/        # 可选：引擎原生索引，如 USearch
└── text/           # 可选：全文索引文件
```

四条不变量值得记住：

- 所有路径都相对 `manifest.json` 所在目录，且必须在包根内；
- 路径只允许 `/`，拒绝绝对路径、盘符、URL scheme、反斜杠与 `..`；
- 所有资源路径在整个包内唯一；
- 数据包不可变：内容变了就是一次新发布，靠目录或入口指针区分版本。

`.wsql` 是可选的分发形态：把同样的目录打成一个文件，读取语义不变。它不是“另一种格式”，只是不同的搬运方式。

## Manifest 声明什么

Manifest 描述的是**数据布局**，不是引擎配置：

| 声明内容 | 例子 | 不包含 |
| --- | --- | --- |
| 格式与版本 | `format: "weisql"`、`formatVersion: "1.0.0"` | SQL 方言、函数列表 |
| 表 | 列名、列类型、可空性、主键、Parquet 路径 | 索引、分区策略 |
| 向量集合 | 维度、度量、编码、向量文件、ID Map | ANN 参数（属于 `index.params`） |
| 全文索引 | 文档数、词项数、平均长度、倒排文件 | 分词器实现 |
| 完整性 | 每个文件的 `bytes` 与 `sha256` | 发布者身份（由签名承担） |

一个关键约束：`data.bytes` 必须等于 `count × dimension × 4`。这不是文档建议，而是校验器会执行的规则；它让“维度写错”这类错误在读取前就暴露。

字段速查见 [Manifest 参考](/docs/reference/manifest)。

## 四层校验

校验不是一个开关，而是四层；失败的位置决定了你能排查什么。

<CardGrid columns={2}>
  <DocCard title="L1 结构" tag="open()" index="01">
    JSON 类型、必填字段、未知字段、版本。典型错误：`MANIFEST_INVALID`、`FORMAT_VERSION_UNSUPPORTED`。
  </DocCard>
  <DocCard title="L2 语义" tag="open()" index="02">
    名称、跨字段引用、路径、计数与字节公式。典型错误：`MANIFEST_INVALID`、`PATH_INVALID`。
  </DocCard>
  <DocCard title="L3 内容" tag="verifyChecksums" index="03">
    实际长度、SHA-256、JSONL 与偏移对应。典型错误：`RESOURCE_INTEGRITY_FAILED`。
  </DocCard>
  <DocCard title="L4 引擎" tag="--l4" index="04">
    Parquet 可读性、列名与类型是否与声明一致；SQL Adapter 打开时或 CLI `--l4`。
  </DocCard>
</CardGrid>

<Callout title="两个容易误解的点">
  **L1/L2 不读取任何资源**，只看 Manifest 文本，所以能在下载数据之前失败。
  **只有 L3 的 `all` 模式能发现同长度的内容篡改**，`manifest` 模式只比对长度。
</Callout>

`verifyChecksums` 三种取值：`none`（默认，只做 L1/L2）、`manifest`（比对长度）、`all`（增量 SHA-256 并校验 ID Map 内容）。完整性校验发生在任何 Adapter 接触资源之前。

## Reader 与 Adapter

<CardGrid columns={2}>
  <DocCard title="ResourceReader" tag="bytes" index="01" to="/docs/api/readers">
    唯一接触字节的抽象：`read` / `readRange` / `stat` / `close`。区间是 `[start, end)`，短读必须失败。
  </DocCard>
  <DocCard title="SqlAdapter" tag="engine" index="02" to="/docs/api/adapters">
    SQL 引擎边界；不注入时 `db.sql()` 返回 `SQL_UNSUPPORTED`。
  </DocCard>
  <DocCard title="VectorAdapter" tag="engine" index="03" to="/docs/api/adapters">
    向量引擎边界；不注入时使用 SDK 内置精确检索。ANN 必须声明 `exactSearch: false`。
  </DocCard>
  <DocCard title="缓存" tag="decorator" index="04" to="/docs/sdk/resource-readers">
    `CachedResourceReader` 做有界 LRU、并发合并与发布版本隔离；`open({ cache })` 自动套用。
  </DocCard>
</CardGrid>

三条边界值得记住：

- **不注入就报错，不返回模拟数据**。宁可失败，也不给假结果。
- **精确与 ANN 必须可区分**。精确实现声明 `exactSearch: true`；ANN 必须声明 `false`。
- **引擎能力通过 `capabilities()` 报告**，而不是靠文档承诺。

## 常见误解

| 误解 | 实际情况 |
| --- | --- |
| “Manifest 是引擎配置” | 它是跨引擎的数据契约；引擎参数只出现在 `index.params` |
| “有 SHA-256 就说明数据可信” | 它只证明内容与声明一致，不证明发布者身份 |
| “SQL 不可用说明数据坏了” | 多半是没注入 Adapter，错误码是 `SQL_UNSUPPORTED` |
| “过滤是查询后再丢弃” | 默认策略先过滤再比较，否则不能声明 `exact` |
| “浏览器和 Node 能力相同” | 结果语义一致，能力边界不同，见[兼容性](/docs/reference/compatibility) |
| “包大就一定会全量下载” | 多文件包按 Range 读取；`.wsql` 整包读取才会全量下载 |
